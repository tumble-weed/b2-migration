B2 de-risk test — prove B2 before moving 600 GB

Written 2026-08-25, in session. Companion to .claude/todo/gdrive_to_b2_migration.md (the migration architecture) and elp_with_scales/.claude/todo/results_payload_shrink.html (what is inside the corpus). This file covers only the small paid experiment that decides whether B2 is safe to commit to. Nothing here has been executed. One action has already been taken outside this test: 211 corpus symlinks were rewritten absolute→relative (see §8).

1  Why this test exists

The goal is to replace Google Drive, not to sit alongside it. That raises the bar: the test has to prove restore is trustworthy, not just that upload is fast.

QuestionWhat answers it
Is B2 faster than gdrive for many small objects? objects/sec on the TINY payload, both backends, both directions
Is B2 faster for few large objects? MB/s on the BIG payload (multipart path)
Does a re-written file cost bandwidth if content is unchanged? no-op re-sync: bytes transferred must be 0
Do old versions actually get purged? overwrite one file, then check versions before/after GC
Does the corpus come back bit-identical? checksum compare on restore, into a scratch dir
What does a full restore cost? bytes transferred × price table (there is no billing API)

2  Decisions already locked (do not re-open)

DecisionChoiceWhy
transfer toolrclone native b2 First-class backend in rclone v1.73.0, same binary already used for gdrive. Filters (--filter-from, --exclude) live in rclone core, so they behave identically on b2 and gdrive. b2sdk is not in the transfer path.
symlinks--links Stores each symlink as a tiny .rclonelink file and recreates the real symlink on download. Pointer round-trips; target data is not duplicated.
archive scopeboth trees results-torchray + results-with-detailed-info. 211 links point from the first into the second; archiving only one leaves 211 dangling links.
versioningdaysFromHidingToDeleting=1 B2 versioning cannot be disabled. Overwrites always create a version, and hidden/superseded versions bill storage. 1 day is the floor.
keysbucket-scoped Master key only for the one-time lifecycle set (needs writeBuckets), then removed from the config.
--fast-listno, not globally Ops are free, so fast-list buys only speed and costs ~1 KB RAM per object (~4 GB at corpus scale). Sync per-method-dir instead; get throughput from --transfers/--checkers. Provisional — taken as a recommendation, revisit if the test shows listing is the bottleneck.
tarring small filesrejected One changed file would force re-upload and re-download of the whole tar. The premise of this work is that results are being re-written, so incremental sync is the thing that must not be traded away.
paymentmanual monthly Indian Visa debit is the weakest case for recurring international charges (RBI e-mandate auto-declines). Treat autopay as a bonus; pay on a reminder. See §7.

Total ~2.86 GB, inside B2's 10 GB free tier, so the test itself is $0. Nothing is copied locally — BIG is selected with --files-from over the live tree, built from the census.

Accepted risk: 10,000 objects measures a rate but will not reveal a throttle wall that only appears at 100k+ objects. The 30k cross-check was declined; if the backfill later stalls, this is the first assumption to revisit.

Timed legs — 2 payloads × 2 backends × 2 directions

#legcommand shape
1TINY up → B2rclone copy --links TINY b2:derisk/tiny
2TINY up → gdriverclone copy --links TINY gdrive:derisk/tiny
3BIG up → B2rclone copy --files-from big.txt / b2:derisk/big
4BIG up → gdriverclone copy --files-from big.txt / gdrive:derisk/big
5TINY down ← B2rclone copy --links b2:derisk/tiny SCRATCH/b2-tiny
6TINY down ← gdriverclone copy --links gdrive:derisk/tiny SCRATCH/gd-tiny
7BIG down ← B2rclone copy b2:derisk/big SCRATCH/b2-big
8BIG down ← gdriverclone copy gdrive:derisk/big SCRATCH/gd-big

Every leg runs with --stats 10s --stats-one-line --log-level INFO --log-file so wall clock, bytes and per-object rate are all recoverable from the log. Record for each:

wall clock | objects/sec | MB/s | bytes transferred | retries | errors

Restores go to a scratch dir only. Never onto the live tree — a restore that lands on results-torchray could overwrite real results.

Behaviour checks (not timed — pass/fail)

checkmethodpass condition
no-op re-sync run leg 1 again, unchanged source bytes transferred = 0. This is what makes re-written-but-identical files free.
changed-file re-sync modify 1 file's content, re-run leg 1 exactly 1 object transferred, not 10,000
version GC after the overwrite: rclone backend lifecycle b2:derisk, rclone ls --b2-versions b2:derisk, then rclone backend cleanup-hidden b2:derisk old version visible before GC, gone after. Confirms the storage double-bill is bounded.
bit-identical restore rclone check --checksum source vs each restored scratch dir; then lzma+pickle.load a sample and compare arrays with (a == b).all() zero differences. Gating check — the plan is to retire gdrive, so a restore that is merely "probably fine" is not enough.
symlink round-trip include one .rclonelink-bearing dir; restore and readlink relative target string comes back byte-for-byte
filter semantics --filter-from with an exclude rule, same file on b2 and gdrive identical file sets on both backends

Cost accounting

There is no billing or pricing endpoint in the B2 API or b2sdk. Cost is computed, not queried:

egress $ = (bytes downloaded beyond the 3x free budget) x $0.01/GB
ops $    = 0

Cross-check the byte totals against the account's Caps & Alerts page, which is the authoritative usage counter. Set caps before the first upload.

6  Setup, in order

# 1. bucket, private, with the master key
rclone config          # remote [b2master], type = b2
rclone mkdir b2master:results-derisk

# 2. one-time lifecycle rule (needs writeBuckets -> master key)
rclone backend lifecycle b2master:results-derisk \
    -o daysFromHidingToDeleting=1
rclone backend lifecycle b2master:results-derisk   # read back, confirm

# 3. bucket-scoped key for everything else
b2 key create --bucket results-derisk rclone-derisk \
    listBuckets,listFiles,readFiles,writeFiles

# 4. second remote using ONLY the scoped key; drop [b2master]
rclone config          # remote [b2], type = b2
chmod 600 ~/.config/rclone/rclone.conf

The rclone config holds live credentials. It is not in any repo and must stay that way.

7  Payment risk — the only failure mode that loses data

B2 is usage-billed monthly, i.e. a recurring international charge. An Indian Visa debit card is the weakest case: RBI's e-mandate rule makes issuers auto-decline standing instructions to unregistered foreign merchants. Month 1 (clicked manually) clears; month 2 (automatic) is the one that fails.

Backblaze's published non-payment phases:

charge fails
  |
  +-- Phase 1  grace. everything still works.
  |            email within 48h, then every 5 days.
  |            (length not published)
  |
  +-- Phase 2  2 weeks. uploads stop, data intact.
  |
  +-- Phase 3  2 weeks. "may be deleted at any moment"
  |
  +-- deleted

Source: help.backblaze.com/hc/en-us/articles/219361957-B2-Non-payment-procedures. Because Phase 1's length is unpublished, budget from the first email, not in weeks. Treat day 1 of Phase 3 as the deadline.

mitigationstatus
pay manually on a monthly reminder; autopay is a bonusdecided
confirm the bank app has international online transactions enabledto do

keep the gdrive copy until two consecutive charges have cleareddecided

Absolute targets would have pinned the archive to this box's mount layout — restore to a different path and all 211 dangle. Relative targets survive any mount point. Script: scripts/relativize_links.py. Rollback manifest (all 212 original targets): scripts/symlinks_before.tsv. Pre-check and post-check both 211/211 resolving; zero absolute links remain. Committed as 2372ba6.

Restore rule this creates. Both trees must land under the same parent: 
<anywhere>/
  results-torchray/
  results-with-detailed-info/
Restore results-torchray alone and the 211 links dangle wherever you put it. Encode this as a guard in whatever restore script gets written.
